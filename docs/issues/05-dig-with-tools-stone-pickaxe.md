# Dig with tools and real hardness: hardness.edn and tool tags from datagen, a pure dig-time formula, tool selection in `:dig`, a safe `:stairs-down` intent, and the stone-pickaxe goal

## Summary

`:dig` today knows exactly one block: a log broken by hand. `src/clojurecraft/intent.clj:17-18` hardcodes `dig-ms 3000` and `finish-after (+ (* dig-ms 1.35) 200)`, `intent.clj:114` always sends `{:packet/name :set-carried-item :slot 0}` whatever is in hotbar slot 0, and `intent.clj:103` refuses any target that is not `blocks/log?`. `resources/clojurecraft/blocks.edn` carries names, definition types and state ranges but no hardness, no "needs a pickaxe", no tool tier. The next goal on the critical path is a stone pickaxe, which needs the bot to dig stone with a wooden pickaxe, know how long that takes, know that stone dug by hand drops nothing, and get down to stone without falling into a cave, a lake or lava.

This issue adds, in order: (1) two generated tables, `hardness.edn` and `harvest.edn`, with stated provenance; (2) a pure `(dig-ms world target held-item)` that reproduces the vanilla breaking formula; (3) a tool table derived from `items.edn` names; (4) tool selection inside `:dig` (choose the best tool for the target, `set-carried-item`, verify against `:player/inventory`, treat a vanished tool as "broke, re-select"); (5) a `:stairs-down` intent that never digs the block under the feet and checks the cells it opens for liquid; (6) a `:cobblestone` goal row (hold 3) feeding the `:stone-pickaxe` goal, which depends on the crafting issue; (7) hardness-aware breaking and held-item tracking in `sim.clj`; (8) specs and properties.

## Why now / what the siblings learned

**The siblings both had to fight hardness.** ruststeve's generated data had placeholder hardness and the dig timer was wrong for everything but hardness-1 blocks. `ruststeve/CHANGES.md:42`: "`data/blocks.json` carries a placeholder hardness — `src/bin/datagen.rs:281` writes 1.0 for every solid block (the vanilla reports have no destroy time) … deepslate (real 3.0) got a 0.25 s estimate, the 1.35×+200 ms hold (0.54 s) landed exactly on the server's 70 % threshold (0.525 s), and natural deepslate digs were rejected about half the time — locally predicted air, then the server's block_update put the block back." Their fix is a 100-line hand table `block_hardness(name)` at `ruststeve/src/bot/mod.rs:2215-2305` plus name heuristics `is_pickaxe_block` at `mod.rs:2306-2318`, which first got the pickaxe family wrong: `CHANGES.md:95` "granite/diorite/andesite/tuff … got the BARE-HAND break time, ~3× too long … 4 s/block through diorite/granite — the same hardness (1.5)". Name heuristics are exactly the kind of hidden table this project refuses.

**typecraft has the real numbers, and they come from the game itself.** `steve/src/lib/typecraft/datagen/mod/src/main/java/dev/typecraft/datagen/DataExtractor.java:70-74` is a Java datagen mod: `float hardness = defaultState.getDestroySpeed(EmptyBlockGetter.INSTANCE, BlockPos.ZERO); obj.addProperty("hardness", hardness); … obj.addProperty("diggable", hardness >= 0);`. The output `steve/src/lib/typecraft/data/blocks.json` (1168 blocks; CI copy in `steve/ci/typecraft-data.tar.zst`) has fields `id, name, displayName, hardness, resistance, stackSize, diggable, boundingBox, transparent, emitLight, filterLight, defaultState, minStateId, maxStateId, states, drops` and no `material`/`harvestTools` field at all, so typecraft's `registry.materials` path in `digging.ts:546-558` is dead and it falls back to name parsing (`getToolSpeed`, `digging.ts:166-218`). Values read from it: stone 1.5, cobblestone 2, dirt 0.5, grass_block 0.6, oak_log 2, oak_leaves 0.2, gravel 0.6, sand 0.5, iron_ore 3, deepslate_iron_ore 4.5, coal_ore 3, obsidian 50, deepslate 3, crafting_table 2.5, furnace 3.5, netherrack 0.4, bedrock -1 (`diggable false`), water/lava 100.

**The harvest rules do not need heuristics: the server jar ships them as tags.** The bundler jar that `scripts/datagen.sh` already downloads wraps `META-INF/versions/26.1.2/server-26.1.2.jar`, which contains `data/minecraft/tags/block/mineable/{pickaxe,axe,shovel,hoe}.json`, `needs_{stone,iron,diamond}_tool.json` and `incorrect_for_{wooden,stone,copper,iron,gold,diamond,netherite}_tool.json`. Read tonight: `needs_stone_tool` starts `iron_block, raw_iron_block, iron_ore, deepslate_iron_ore, lapis_…, copper_…`; `needs_iron_tool` is diamond/emerald/gold/redstone ores and blocks; `needs_diamond_tool` is `obsidian, crying_obsidian, netherite_block, respawn_anchor, ancient_debris`; `incorrect_for_wooden_tool` = needs_stone + needs_iron + needs_diamond; `incorrect_for_stone_tool` and `incorrect_for_copper_tool` are identical (needs_iron + needs_diamond); `incorrect_for_iron_tool` = needs_diamond; `incorrect_for_diamond_tool` is empty. So copper tools (new in this version: `items.edn` has `:copper_pickaxe 919`) harvest the same set as stone. `mineable/shovel` is 21 entries (dirt, grass_block, gravel, sand, …); `mineable/pickaxe` begins `stone, granite, …, cobblestone, gold_ore, …, iron_ore, coal_ore`.

**The dig-time formula is the same in both siblings and matches vanilla.** typecraft `digging.ts:618-625`: `const damage = speed / hardness / (canHarvest ? 30 : 100); if (damage >= 1) return 0; const ticks = Math.ceil(1 / damage); return ticks * 50;` with `speed *= 0.2` for eyes in water without Aqua Affinity (`digging.ts:595-610`, note the comment: "Vanilla applies it when the EYES are in water (isEyeInFluid) … Using isInWater here made the client wait 25× for a dig the server completes at 5×") and `speed *= 0.2` when not on ground (`digging.ts:613-615`). Tier multipliers `digging.ts:13-20`: wooden 2, stone 4, iron 6, golden 12, diamond 8, netherite 9. ruststeve `mod.rs:1831-1849` is identical and adds the key rule "the TOOL decides harvestability, not the penalized speed". Durabilities from typecraft `items.json`: wooden 59, stone 131, copper 190, iron 250, golden 32, diamond 1561, netherite 2031.

**Two protocol facts the siblings paid for.** (a) The selected slot drifts: `digging.ts:366-371` "The server's SelectedItemSlot was observed drifting from the client's quickBarSlot (a bot digging 'with a stone pickaxe' while the server had andesite selected), so every client-side dig time was too short, the server rejected the break, and the client kept a phantom air block under its feet. One packet makes them agree." steve `tasks/mining/main.ts:180-196` `ensurePickaxe` goes further: equip, then if the held item still is not a pickaxe, resync the inventory and retry once. ruststeve `bot_utils.rs:667-689` `select_item` loops up to 5 times until the server-confirmed held item matches, swapping from the main inventory with a hotbar-swap click (mode 2) when the tool is not in the hotbar. (b) No echo to the breaker and the late-STOP rule: `mod.rs:1683-1687` "a STOP that arrives before the server is done ABORTS the break … while a late STOP is accepted" and `mod.rs:1718-1727` "the server breaks the block in response to FINISH but does NOT echo a block_update back to the breaking player … Reflect the break locally". Our `intent.clj:133` already does the local set-block; the rejected case (a `block-update` restoring the target after FINISH) is not handled anywhere today.

**Tool wear is a race-scale fact.** `CHANGES.md:68`: "one natural trial = ~550 digs … more than two iron pickaxes (2 × 250). With both gone, deepslate digs FAIL outright … Every dig after that was bare-hand stone: `descend_to_y` at ~44 s per block". `mining.rs:181-205` and `main.ts:231-256` (`ensureSparePickaxe`) both re-equip after a break and bail to re-craft rather than dig stone by hand. The cheapest version of that for us is: a tool that vanishes from the inventory is "broken", the planner re-derives.

**Digging down is where bots die.** ruststeve `mining.rs:82-150` `dig_down`: uses `(p.y - 0.5).floor()` for the support block ("physics jitter dips position.y just under the integer"), digs every cell under the 0.6-wide footprint ("Digging only floor(x),floor(z) leaves an adjacent sub-cell holding the bot up"), refuses if the cell or the cell below is liquid or lava is beside it, refuses over a 3-deep air column, never digs obsidian, and reports success only if `position.y < y_before - 0.5` ("Digging stone with no (or the wrong) tool doesn't break the block, so the bot never falls — returning true there spins"). `mining.rs:265-300` `descend_step` is the stair variant: open head+1, head, feet ahead, refuse if any of the four cells ahead is liquid, step down one. steve `main.ts:258-375` `descendStaircase` "Never digs the block directly under the bot's feet (avoids blind drops)", checks five cells of the next step for lava and for water ("water in the step floods the 1-wide shaft and drowns us"), scans a drop column to its floor and refuses water or lava there or a drop ≥ 4, rotates direction when boxed, and gives up after 4-6 rotations. `main.ts:1093-1107` `digDownVertical` adds "it lands (waits for onGround) before each dig, because typecraft applies a 5× 'not on ground' mining penalty … mining mid-fall made a naive straight-down dig ~3s/block" and stands in the cell centre first.

## Design

**Data first: two new generated tables, written by `dev/clojurecraft/datagen.clj`, with a provenance header.**

- `resources/clojurecraft/hardness.edn` `{block-name hardness}` (double; -1.0 for unbreakable). Source: typecraft's `blocks.json` (vendored copy committed under `dev/data/typecraft-blocks.json` or read from `steve/ci/typecraft-data.tar.zst`; the header names the file, its sha1, the DataExtractor commit and the `getDestroySpeed` call), keyed by `name` and joined to our `blocks.edn` names; datagen fails loudly on any name in `blocks.edn` missing from the source so a version bump cannot silently default to 1.0 (the exact ruststeve bug). Provenance note in the header: "hardness is not in the vanilla --reports; these values are `BlockState.getDestroySpeed` read by typecraft's datagen mod against 26.1.2".
- `resources/clojurecraft/harvest.edn` `{block-name {:tool :pickaxe|:axe|:shovel|:hoe :needs :stone|:iron|:diamond}}`, built by unzipping the inner jar's `data/minecraft/tags/block/mineable/*.json` and `needs_*_tool.json` (datagen.clj gains a `tags` reader that expands `#minecraft:` references). `:needs` absent means no requirement. This is the jar's own data, same provenance as `blocks.edn`.
- `blocks.clj` gains `hardness`, `tool-of`, `needs-tier` lookups by state id (arrays built like `solid-flags`), and `blocks/tools` `{item-name {:tier :wooden|:stone|:copper|:iron|:golden|:diamond|:netherite :kind :pickaxe|:axe|:shovel|:hoe|:sword}}` derived from `items.edn` names by splitting on `_` (every `*_pickaxe` etc.), plus `tier-speed {:wooden 2.0 :stone 4.0 :copper ? :iron 6.0 :golden 12.0 :diamond 8.0 :netherite 9.0}` and `tier-rank` as `def`s with a comment (copper: see open questions).

**A pure formula.** `(dig/ms world target held)` in a new `dig.clj`: `speed` = tier speed when `(tool-of state)` equals the held tool's `:kind`, else 1.0; `/ 5` when the eye block is water; `/ 5` when `(not (:player/on-ground? world))`; `harvest?` = no `:needs` or `(>= (tier-rank tier) (tier-rank needs))`; `damage = speed / hardness / (if harvest? 30 100)`; `0` if `damage >= 1`, else `(* 50 (Math/ceil (/ 1 damage)))`; `nil` for hardness < 0. Also `(dig/drops? state held)` = `harvest?`. Every input is in the world value or the argument list; no clock, no registry object. Worked numbers for tests: oak_log by hand 3000 (matches today's constant), oak_log wooden axe 1500, dirt by hand 750, stone by hand 7500 and no drop, stone wooden pickaxe 1150, stone stone pickaxe 600, cobblestone wooden 1500, cobblestone stone 750, iron_ore stone pickaxe 1150, iron_ore wooden pickaxe 7500 and no drop, obsidian diamond 9400, obsidian iron 41700 and no drop, off-ground stone wooden pickaxe 5750.

**`:dig` gains tool selection.** New keys beside the old ones (never a changed meaning): `:intent/tool` (item id chosen), `:intent/slot` (hotbar index), `:intent/dig-ms`. In `:settle`, pick the inventory slot holding the best tool for the target (`dig/best-tool`: lowest dig-ms among held items that harvest, else bare hand; refuse with `:needs-tool` when nothing held harvests a block that `:needs` a tier, so the planner can re-plan instead of spending 7.5 s for nothing); if it is in the hotbar emit `set-carried-item` with that slot, else fail `:tool-not-in-hotbar` (moving items is the crafting issue's window-click work; crafted tools land in the hotbar first per vanilla `quickMoveStack`, so this is rare on our path). Record `:player/carried` on emit so the bot knows what the server thinks it holds. In `:digging`, `finish-at` = `(+ now (* 1.35 dig-ms) 200)` from the formula instead of the constant; the target check uses `(= state at-target)` captured at start instead of `log?` so any block kind can be dug. After FINISH, a new stage `:confirm` waits up to 10 ticks: a `block-update` restoring the target (`game/block-at` non-air again) means the server rejected the break; fail with `:rejected` so the planner retries with a fresh dig rather than walking into ghost air (the ruststeve suffocation cases, `CHANGES.md:67,77`). Tool break: if `(get-in world [:player/inventory slot :item])` is no longer the chosen tool mid-dig, fail `:tool-broke`; the next `:settle` selects again.

**`:stairs-down` intent.** `{:intent/kind :stairs-down :intent/to-y n :intent/dir [dx dz]}`; one stair per cycle, composed of the existing primitives as sub-steps in the intent value (`:intent/stage :clear-head-up | :clear-head | :clear-feet | :step | :check`), each dig delegated by building a child `:dig` map and running `intent/run` on it (intents composing intents, no new executor logic for breaking). Rules, all pure checks on `game/block-at` and `memory/remembered`: never dig `[x (floor (- y 0.5)) z]` (the support); refuse the step if any of the four cells ahead (`y+1 .. y-2`) is water or lava or unloaded (`nil` is unknown, and unknown is not safe); refuse if the cell ahead at `y-2` opens on an air column deeper than 3 or whose floor is liquid; rotate `:intent/dir` 90° on refusal and fail `:boxed` after 4 rotations; verify descent by `(:player/pos world)` y dropping, exactly ruststeve's "only report success if we ACTUALLY descended"; stop when feet y ≤ to-y. Liquids are detected by block type `:liquid` from `blocks.edn` (already in `passable-types`). Gravel/sand above the head cell is left as an open question.

**Goal rows** in `plan/goals`: `{:goal/id :cobblestone :goal/priority 2 :goal/doc "hold 3 cobblestone"}` with `goal-done?` = `(>= (game/held world :cobblestone) 3)` and `next-intent` = walk to the nearest remembered stone (memory `watched?` extends to the `mineable/pickaxe` set, bounded by only recording stone adjacent to air so the store stays small) or `:stairs-down` to the first stone layer when none is exposed, then `:dig` + `:collect`; preconditions `(held? :wooden_pickaxe)` else `{:plan/wait :no-pickaxe}`. `{:goal/id :stone-pickaxe :goal/priority 3}` is `:cobblestone` ×3 + sticks ×2 + a table craft and lives in the crafting issue; this issue stops at "3 cobblestone held with the wooden pickaxe still in hand".

**Sim extension.** `sim.clj` tracks `:sim/carried` from `set-carried-item`, `:sim/inventory` (so held item is known), and breaks on FINISH only if `(>= (- now at) (* 0.7 (dig/ms …)))` using the same pure formula with the sim's own view of ground/water (the 70 % server threshold, cited above); a rejected FINISH sends a `block-update` restoring the block (the real server's behaviour) instead of silently dropping the dig; a bare-hand FINISH on a `:needs` block breaks the block but drops nothing; each accepted dig with a tool decrements `:sim/durability` and empties the slot at 0 with a `set-player-inventory`. The existing `an-early-finish-does-not-break-the-block` test stays green and gains the restoring block-update.

**Specs.** `:intent/tool int?`, `:intent/slot (s/int-in 0 9)`, `:intent/dig-ms nat-int?`, `:intent/to-y int?`, `:intent/dir` one of the four unit vectors, `:player/carried (s/int-in 0 9)`; `s/fdef dig/ms` with `:ret (s/nilable nat-int?)`; `:goal/needs`-style preconditions stay data.

## Acceptance criteria

- Unit: `dig/ms` reproduces every row of the worked table (log/dirt/stone/cobblestone/iron_ore/obsidian × hand/wooden/stone/iron/diamond, plus the ×5 water and ×5 off-ground cases); `harvest?` is false for stone by hand, iron_ore with wooden, obsidian with iron, and true for the correct tiers; copper equals stone for `harvest?`.
- Property (`props_test.clj`): for any generated block state with hardness > 0, any held item and any tick sequence, the `:dig` executor never emits a `player-action` status 2 before `(+ started (* 1.35 (dig/ms …)) 200)`; it never emits status 0 for a block it cannot harvest when the block `:needs` a tier; `finish.sequence = start.sequence + 1`.
- Sim e2e: starting with a wooden pickaxe, the composed reducer reaches `plan/done?` for `:cobblestone` with ≥ 3 cobblestone in `:player/inventory` and the pickaxe still held; starting bare-handed it waits `:no-pickaxe` and never digs stone.
- Sim e2e: `:stairs-down` over a lava-floored cell never digs that cell and ends `:boxed` when all four directions are unsafe.
- Live: one recorded local run reaches 3 cobblestone with `RESULT :ok true`; `clojure -M:replay` on the recording gives the same RESULT.
- CI: the `cobblestone` job passes on a fresh vanilla 26.1.2 server with the independent RCON judge.
- Replay and purity are intact: no reducer reads a clock, `rand`, or a registry object; `hardness.edn` and `harvest.edn` are regenerated by `scripts/datagen.sh` and never hand-edited.

## Open questions

- Copper tier speed: the siblings predate copper tools and the tag data only fixes its harvest level (= stone). The multiplier (believed 5.0) is in `ToolMaterial` code, not a data file; read it from the jar (reflection against the inner jar, or one timed live dig) before committing a number.
- Should an early FINISH be modelled as "rejected" or as vanilla's delayed destroy (the server keeps breaking on its own after an early STOP in some paths)? The siblings observed rejection in practice; the sim models rejection until a recorded live run says otherwise.
- `:intent/tool` not in the hotbar: fail and leave it to the crafting issue's window clicks, or send `pick-item-from-block` (present in `packets.edn` c2s 36), which swaps a matching inventory item into the hotbar server-side with no window transaction?
- Durability: slots arrive with `:components? true` but `packet.clj:106-111` does not decode the `damage` component, so wear is invisible until the tool vanishes. Is "vanished = broke" enough for the stone-pickaxe goal, or should the spare-pickaxe rule (ruststeve: ≥3 before the portal) come now?
- Memory growth: recording every exposed stone block is far larger than logs. Cap by radius, or only remember stone that `:stairs-down` opened?
- Falling blocks (gravel/sand) above a cleared head cell: refuse the step, or dig and wait a tick for the fall as steve does (`main.ts:831`)?
