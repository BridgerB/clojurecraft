# The Hickey way: how Rich Hickey would build a Minecraft-winning bot, versus what this rewrite did

This is a design essay for clojurecraft. It is built from Hickey's own talks and code (sources at the end), applied to one concrete problem: an autonomous program that has to get from a fresh spawn to a dead Ender Dragon, over hours, against a server that never stops sending it information. The first section lays out the handful of commitments he has repeated for fifteen years. The second holds steve (the TypeScript bot) and the current clojurecraft code up against them, including where the rewrite is still TypeScript wearing parentheses. The third is the design he would actually ship for the large version of this project.

## Hickey's commitments, as they apply to a bot

**Simple means not braided.** His word is *complect*: "It means to interleave or entwine or braid. This is where complexity comes from: complecting." Simplicity is not a count of parts or lines; "simplicity is not about counting." It is about whether each piece is about one thing, so that you can reason about it alone. He is blunt about ownership: "It's your fault if you don't have a simple system." For a program that has to survive two hours of unattended play, this is not aesthetics. "How can we possibly make things that are reliable that we don't understand?" A speedrun bot dies at the fiftieth step because something braided at the fifth. The question to ask of every namespace is: what two things did I just entwine, and will I be able to pull them apart at 3 a.m. when the race log shows the bot standing in lava.

**State complects value and time; values are the escape.** "Having state in your program is never simple because it has a fundamental complecting that goes on in its artifacts." The fix is the epochal time model from *Are We There Yet*: "Actual entities are immutable," "The state is a snapshot," and process is "We take a function of the past, we produce the future." An identity is "a mental construct," a name we give to a succession of values. Time constructs (compare-and-swap, agents, STM) have one job: "to make sure that you have atomic succession of values." The payoff he cares about most is that observers need no coordination: "perception is uncoordinated," "Perception does not interfere with process," "readers don't impede writers." A dashboard, a telemetry writer, a replay recorder: none of them should be able to slow or corrupt the bot, because they only ever look at values.

**Programs are about information, and information is sparse, open, and named.** *Effective Programs* defines his target: "Clojure's target is information-driven situated programs," things that "run on an ongoing basis and they're sort of wired up to the world" and "deal with real-world irregularity." A Minecraft bot is a textbook situated program. His conclusions follow: "just use maps," "Inherently, information is sparse," "positional semantics don't scale," and "types are an anti-pattern for program maintenance and for extensibility." In *Maybe Not* he turns this on aggregates themselves: maps "should not be denigrated. They should be exalted"; product types "complect the meaning of things with their position"; "it is a mistake to put optionality in aggregate definitions" because the same aggregate is reused in many contexts; "optionality is context dependent"; missing data should simply be absent ("You want to leave it out. The maps know what they know"); and "Spec is an open system," so extra keys are never an error. Schema (the shape of an attribute) and selection (what a given function requires) are two different things, and conflating them produces the brittle nested records that every TypeScript codebase accumulates.

**Design is taking things apart.** *Design, Composition and Performance* goes to the etymology: to design is to mark out, to separate, and good design "is about taking things apart in such a way that they can be put back together." Each component is about one or very few things. Decompose first, compose second, and the decomposition should keep paying off as the program grows. The complement is *Hammock Driven Development*: state the problem, in writing, before touching code; the ability to solve hard problems "is directly correlated with the amount of time spent thinking about those problems." For the dragon, the problem statement is not "chop wood, craft, build portal." It is: *act usefully under partial, delayed information about a world that changes while you are not looking, and recover from any step failing.*

**Systems are processes connected by queues, speaking data.** *The Language of the System*: "We're just going to talk with data"; queues "are completely decoupling"; "this notion of flow, I think, is the key to keeping systems sorted"; "the epochal time model, the one that's behind Clojure, it works in systems"; and the sobering "distributed error modes are the only error modes." The core.async talk is the in-process version: "There's no shared state except for these channels"; conveyance should be first class; callbacks are bad because they force you "to break your logic up into little pieces so that those pieces of logic can live inside handlers"; "Don't put any logic in your handlers"; and "we do not provide and will not provide are unbounded buffers. This is just a recipe for a broken program."

**Grow, never break.** *Spec-ulation*: "Breaking changes are broken." Change comes as accretion (provide more), relaxation (require less), or fixation (fix a bug); anything else is a new name. "The namespace is part of the name." For a long-lived bot this means a world key never changes meaning, a packet spec is only ever extended, and a goal that stops working is given a new name next to the old one rather than silently redefined.

**His code, not just his talks.** The ants simulation (2008) is the clearest sample of how he writes a world. The world is "a 2d vector of refs to cells," a cell is a tiny struct with optional keys ("`;may also have :ant and :home`"), every lookup goes through one helper (`place`), tunables are top-level `def`s with a comment ("`(def evap-rate 0.99)`"), names are short and domain-flavored (`dir-delta`, `wrand`, `bound`, `pher`), and the behavior loop is a function that does its one transaction then reschedules itself ("`(send-off *agent* #'behave)`"). The UI comes after a banner comment, depends on the model, and the model never depends on it; `render` takes one consistent snapshot in a transaction and draws from the copy. Comments state invariants ("Must be called in a transaction that has verified the way is clear"). No records, no macros beyond the one he needed, no framework, under 250 lines. The clojure.org rationale sums the preference: "Many functions defined on few primary data structures," "Mutable stateful objects are the new spaghetti code," "Object Orientation is overrated."

## Steve, clojurecraft, and the honest gap

**What the TypeScript way braids.** steve is organized around a `bot` object. Position, inventory, entities, chunks, control state, the physics interval, the socket, event listeners and the dig timer all live on it, and they change in place. Tasks are closures over that object: `gatherWood(bot, 5)` reads `bot.entity.position`, calls `bot.lookAt`, flips `bot.setControlState("forward", true)`, awaits `bot.dig(block)`, and polls `bot.inventory`. The 31 steps are objects with `canExecute`, `isComplete` and `execute` methods. Bot memory is a `WeakMap` keyed on the object. Telemetry is an imperative `logEvent()` call sprinkled through the tasks. Physics runs on `setInterval` and sends packets from inside its own tick. Every one of these is a braid in Hickey's sense: identity and value (the bot *is* its state), computation and effect (deciding to dig and sending the dig packet are the same line), logic and conveyance (handlers on `bot.on("blockUpdate")`), and time and value (the only way to know what the bot thought at second 3,412 of a race is to have logged it at second 3,412). Three things in steve are nonetheless already Hickey-shaped, and worth keeping: `completedSteps` is re-derived from `isComplete()` every tick rather than stored, so a step is "done" only while the world confirms it; the run loop is a CSP go-loop with an epoch counter that discards stale results; and typecraft's `blockSeen` is passive accumulation of sightings rather than scanning. Those are values-and-time instincts fighting their way out of an object.

**What clojurecraft got right.** The world is one immutable map in one atom, and only the loop thread writes it. The protocol is `(step state event) → {:state :effects}`, a pure function; the goal is a second function with the same signature composed after it, so the two can be tested with canned events and no socket. Packets are flat maps; packet specs are a data table with one interpreter; packet ids are generated from the server's own reports; unknown packets become `{:name :unknown}` and are counted rather than thrown. Time enters only as `[:tick now]`, and every deadline is an absolute millisecond value in state, so a dig timeline is reproducible from a list of ticks. Physics is a pure function of the previous player value, the controls and a solidity oracle. I/O is confined to three namespaces. The dependency list is core.async and nothing else. The chunk section is kept exactly as it arrived (palette plus bit-packed longs) and indexed on demand, which is his "arrays in the hot path, values at the interface" pattern. Unknown chunks are `nil`, and physics treats `nil` as solid, which is "the maps know what they know" applied to the world.

**Where it is still TypeScript.** Honesty is the point of this section, so here is the list, roughly in the order he would raise it.

First, the state is *nested*: `{:player {:pos ... :on-ground? ...} :task {:phase ...}}`. *Maybe Not* argues against exactly this. Nesting makes every consumer know the path, makes selection awkward, and turns "which keys does `wood/step` actually require?" into something you can only learn by reading the code. His shape is flat, namespaced, open: `:player/pos`, `:player/on-ground?`, `:task/phase`, `:task/target`, with specs on each attribute and `select`-style requirements per function. It also makes the world printable and greppable, which matters more at hour two than at minute one.

Second, effects are smuggled *inside* the state value under a private key and stripped out by `step`. It works, but it braids "what is true" with "what I want to say." A cleaner shape is for handlers to return `[state effects]` explicitly, or for the outbox to be an honest, named part of the model (`:conn/outbox`) that the loop drains. Hidden keys are the Clojure equivalent of a private field.

Third, the wood policy is a hand-rolled state machine: a `case` over `:phase` with a `cond` per phase and a dozen bookkeeping keys (`:best-dist`, `:best-tick`, `:detour-until`, `:still`). That is "conditionals are complex; rules can be simpler" in the flesh. It is fine for one goal. It will not survive thirty-one. Worse, it calls `rand-nth` for the detour yaw inside what is supposed to be a pure reducer. Randomness is an input; it belongs in the event (`[:tick now seed]`) or in the controls, never conjured inside `step`. Right now a replay of the same event log can diverge, which throws away the single biggest benefit of the design.

Fourth, dispatch is a closed map of handlers keyed by `[phase name]`. Closed is the opposite of "Spec is an open system." A multimethod on the same key is the same amount of code and lets a new namespace add handling for a packet without editing `game.clj`. The same applies to intents: `walk`, `dig`, `collect` should be an open set.

Fifth, there is no spec, no generative testing, no simulation testing, and no recording. Every one of those falls out of the design for free, and none has been written. The example-based tests check a handful of timelines; a property test would check that *every* keep-alive in *any* generated event sequence is answered, that the phase never leaves the transition table, and that `step` never throws for any decodable packet.

Sixth, the world has no memory. `:chunks` and `:blocks` are the current snapshot; a chunk that unloads takes every log it contained with it. steve's `WeakMap` memory is bad because it is a mutable side table, but the need it serves is real. Hickey's answer is Datomic-shaped: facts with time, accumulated, never overwritten.

Seventh, the harness (RCON `locate`, teleport) runs in the same process as the bot, on a side thread poking at the atom. He would make the fixture its own process that speaks to the bot through a queue, so that the test and the thing under test cannot share anything but data.

None of this means the rewrite is wrong. It means the first 5,000 lines established the invariants and the next 5,000 need to stop carrying the habits that typed-object code leaves in your hands.

## The design he would ship for the whole run

**Start with the information model, in writing, before any task.** What does the bot know, and what is each thing's lifetime? Facts about blocks (seen at time *t*, at position *p*, state *s*), facts about itself (position, health, inventory slots), facts about entities, facts about the server's responses to its own actions (ack of sequence *n*, block broke, item picked up), and facts about its own intentions (planned, started, finished, abandoned, why). Write the attribute list with namespaced names and one-line meanings. Everything after this is a function over that model.

**Make the world a fact store, not a snapshot.** The smallest honest version is a map from attribute to value, flat and namespaced. The version that wins the race is an append-only set of `[entity attribute value tx]` facts with a Datalog on top (DataScript is the in-memory incarnation). Then "the nearest oak log I have ever seen that I have not confirmed gone" is a query, not a scan plus a side-table. "Where was lava within 200 blocks of the last water I filled a bucket from" is a query. "What was I trying to do when I died" is a query *as of* the tick before death. The chunk sections stay as raw values for physics and reach checks (hot path), and sightings are derived from them on load, exactly as typecraft's `blockSeen` does, but written into the store as facts rather than into a `WeakMap`. Nothing is ever deleted; a block observed as air at a later time simply supersedes, and the history remains for debugging.

**Keep the epochal loop, and let everyone watch.** `(swap! world step event)` stays the only write. The dashboard that steve builds with a database and SvelteKit becomes `add-watch` on the atom plus a render function that takes a snapshot, which is exactly how the ants `render` works. Telemetry becomes a watcher that diffs successive values and writes facts. Neither can slow the loop or see a torn state, and neither is mentioned in the game code at all.

**Record everything, replay anything.** Because every input is an event value, a recorder is a channel tap that appends each event (and each produced effect) to an EDN file. A two-hour race becomes a file. Debugging becomes `(reduce step init events)` at the REPL with a breakpoint on the tick you care about, with no server. This is the Simulant idea at bot scale: the inputs are data, the code is a value you can point at, so any run is reproducible by anyone later. The current clojurecraft cannot do this only because of the `rand-nth`; fix that and the recorder is twenty lines.

**Goals are data; planning is a function; executing is open.** steve's steps already encode the right idea (a step is done only when the world says so), but as objects with methods. The Hickey form is a vector of maps:

```clojure
{:goal/id :wooden-pickaxe
 :goal/needs {:item/planks 3 :item/stick 2 :block/crafting-table :near}
 :goal/provides {:item/wooden-pickaxe 1}
 :goal/done? :wooden-pickaxe-held?}
```

with `:goal/done?` naming a predicate in a registry, so the goal table is pure data (printable, diffable, loadable from EDN, extensible from another namespace). The planner is `(plan world goals) → intent`: pick the highest-priority goal whose needs are met and whose done predicate is false, and emit a data intent such as `{:intent/kind :dig :intent/pos [x y z]}`. The planner runs every tick against the current value, so "done" is re-derived, regressions re-plan automatically, and nothing is remembered that the world can tell you. Executors are a multimethod on `:intent/kind`, each a small reducer from `(world intent event)` to `(world' effects)`. `walk`, `dig`, `place`, `craft`, `use-item`, `cast-obsidian` are peers; a new kind is a new `defmethod` in a new file. The thirty-one steps shrink to a table and a dozen executors. This is "rules rather than conditionals" and "polymorphism à la carte" in one move.

**Intents are values with time, not timers.** A dig is `{:intent/started t :intent/finish-at (+ t 4250) :intent/next-swing ...}` and the executor compares against `:now`. There is no `setTimeout`, so there is nothing to cancel on death; the next value simply lacks the intent. The epoch counter steve needed to discard stale callbacks disappears because there are no callbacks.

**Spec the boundaries, then generate.** Spec every packet map, every event, every world attribute and every intent; `fdef` the reducers; and write properties, not examples: every keep-alive produces exactly one keep-alive reply; the protocol phase only ever moves along the transition table; `step` is total over the generator of decodable packets; a dig intent never emits FINISH before its deadline; the planner never selects a goal whose needs are unmet. Then build a *server model*: a second pure reducer that consumes the bot's outgoing packets and produces inbound ones (teleport acks, chunk loads from a generated world, block acks, item drops with pickup delay). Bot and server model composed through a channel pair are a complete simulation with no Java process, and test.check can drive it for thousands of generated worlds in the time one real run takes. The real server is kept for the final judge, as it is now.

**Conveyance, bounded.** Socket to decoder to reducer is a pipeline of channels with bounded buffers so that TCP backpressure reaches the reader, as it does today. Chunk decoding sits on the reader thread (it is about bytes, not about the game), so a burst of 200 chunks cannot starve a keep-alive. For a multi-bot race, each bot is its own atom and loop, and bots share nothing but a channel for the one thing they need to share (claimed landing cells). That is the ants design: many agents, each rescheduling itself, coordinating through values.

**Accrete.** `:player/pos` means feet-center forever. If a better representation is needed, it is `:player/aabb`, added beside it. A packet spec only ever gains fields. A goal that was wrong is retired by giving the fixed one a new id and leaving the old id in the table marked superseded, so a recorded race from last month still replays. The generated EDN tables are regenerated per server version and committed, and the protocol number is a key in them, not a constant in the code.

**Style, line by line.** Names from the domain, short, with the namespace carrying the context (`chunk/block-at`, `physics/step`, `wood/find-log` are right; `on-settle` is a phase name leaking into a function name). Docstrings on every public function stating the invariant, the way the ants file says what must already be true when you call it. Constants as `def`s at the top with a one-line comment. `cond` over nested `if`; `reduce` over `loop` unless the loop is hot; type hints and primitive arrays only where a profiler pointed; no macros (the whole project needs none); no records (a map with namespaced keys is the record); `defn-` sparingly, since hiding a function from the REPL hides it from you too. Namespaces as the unit of design, each about one thing, ordered top-down from data to helpers to the one entry point, with the impure part last and clearly fenced the way `;;;; UI ;;;;` fences the ants.

**And the hammock.** Before the portal, before the fortress, before the stronghold, each one gets a written problem statement: what information it needs that the bot does not yet gather, what can go wrong, what "done" means in world terms, and what the recorded-and-replayed failure of the previous attempt showed. The research the siblings did (cast obsidian rather than mine it; the early-FINISH abort; the `attack` packet split in 775; water physics) is exactly this kind of knowledge, and the right home for it is not a comment in a method but a fact in a design document next to the goal table, so the next person reads the decision and not the scar.

**What to change in clojurecraft next, in order.** Flatten and namespace the state and spec it. Move randomness into the tick event and add the recorder. Replace the handler map and the task phases with a multimethod on intent kind and a goal table. Turn `:blocks` sightings into timed facts and add the Datalog. Write the server model and the first five properties. Then, and only then, the second goal.

## Status

The rewrite that followed this essay (same day) did the first five items on the list above: the world is flat and namespaced and specced (`spec.clj`); randomness rides on the tick event and every run can be recorded and replayed (`record.clj`, `--record`, `clojure -M:replay`); packets, intents and goals dispatch through multimethods with the goal table in `plan.clj`; sightings are timed facts in `memory.clj` that outlive chunk unloads (Datalog is still a future swap inside that namespace); and the whole bot runs against a pure server model in `sim.clj` with properties in `props_test.clj`. The harness is an observer of the atom that speaks to the loop only through the events channel. Next are the second goal and the Datalog store.
