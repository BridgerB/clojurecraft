# Entities

Issue #258. Until then `:world/entities` held item drops only (`add-entity` dropped every other type); combat, blazes, endermen and the dragon need every entity.

## What is kept
- `add-entity` keeps every entity: `{:entity/type :entity/pos :entity/seen-at}`, plus `:entity/vel` from the packet's velocity. The bot's own player is never added (the server does not send it), so `track` ignores packets about ids it does not hold.
- `set-entity-motion` sets `:entity/vel`; `teleport-entity` sets position and velocity, each axis relative when its Relative bit says so (X 1, Y 2, Z 4, the deltas 32, 64, 128), as the player's own teleport reads them; `move-entity-pos*` and `entity-position-sync` move it as before.
- `set-entity-data` gives `:entity/flags` (index 0, the shared flags byte: 1 on fire) and, for a living type only, `:entity/health` (index 9, a float). Living means a type in `blocks/mobs`, generated by `jar-probe/mobs` from the game's `DefaultAttributes` (every entity with attributes, and only those, is living), with its maximum health and `MobCategory`. The same index 9 is an interaction's height, so health is never read off a type with no attributes.
- `entity-event` status 3 is a living entity's death: `:entity/died-at`, before the server removes the body. `remove-entities` drops it; a respawn clears them all.

## The wire facts (read from the 26.1.2 jar, probe run 38876275250)
- Velocities are an **LpVec3** (`bytes/read-lpvec3`), not three shorts in 1/8000 blocks as before 1.21.9: one zero byte is the zero vector; else 6 bytes give the scale's low bits, a continuation flag (a varint with the scale's higher bits follows) and three 15-bit components over the scale. Units: blocks a tick.
- `add-entity` after x y z: velocity, pitch, yaw, head yaw (bytes), data varint. `teleport-entity`: id, PositionMoveRotation (x y z dx dy dz f64, yaw pitch f32), Relative set u32, on-ground. `entity-event`: id **i32**, status i8.
- Metadata entries are `[index u8][serializer varint][value]` until index 255. Serializer ids: byte 0, int 1, long 2, float 3, string 4, optional component 6, item stack 7, boolean 8, direction 12, pose 20. `read-metadata` reads the simple ones and stops at the first other (a custom name at index 2 hides the health after it). Living entities: 8 living flags, 9 health, 10 effect particles; mobs 15 mob flags.

## The questions (`entity.clj`)
- `hostiles` - `{eid entity}` alive, of category `:monster`, not `neutral` (enderman, zombified piglin: they leave a player alone until provoked).
- `nearest` - `[eid entity]` nearest a point, within an optional radius.
- `gone?` - removed, or dead by the server's word: a kill is the target being gone.
- `kind`, `item?`, `living?`, `dead?`, `on-fire?`.
- `healths` - `{kind health}`, the nearest of each kind with a known health: the RESULT's `:mobs`.

## Proven on real servers
The gym's `entities` row ([[gym-on-runners]]): a summoned pig at a health no natural pig has; the goal (`:entities`, an aside: `plan/aside?` keeps it out of every run's chain, `observe.clj`) is done once a living entity within 4 blocks has a known health (entities round the spawn it joined at stay tracked until removed: batch entities-258a run 4 ended on one of them, 4/5), and the server's `data get entity` must report the health the RESULT names.

## Gotchas
- `intent/nearest-item` filters `entity/item?`: with every entity tracked, a pig beside a drop is not the drop ([[collect-intent]]).
- Health is the server's word; it is never predicted after a hit.
